OVERVIEW

What does it do?

The Problem

  • Stock prices change hundreds of times per second
  • You need the latest price instantly for dashboards
  • You also need full history for charts and analysis
  • One database can't serve both optimally

The Solution

  • WebSocket — Alpaca pushes every tick to us live
  • Redis — stores only the latest price per symbol, sub-ms reads
  • TimescaleDB — stores every tick ever, optimized for time-range queries
  • React UI — polls both, shows live prices + history

TRANSPORT LAYER

WebSockets — why not HTTP polling?

HTTP Polling (bad)

→ GET /prices (every 100ms)

← 200 OK

→ GET /prices

← 200 OK (same data)

→ GET /prices

10 req/s × 5 symbols = 50 req/s wasted

WebSocket (good)

→ Upgrade: websocket

← 101 Switching Protocols

─── connection stays open forever ───

← {"T":"q","S":"AAPL","bp":250.01}

← {"T":"t","S":"TSLA","p":362.40}

← {"T":"q","S":"MSFT","bp":361.00}

Alpaca pushes every event the moment it happens. The feed client sits in async for raw in ws — the event loop suspends that coroutine until a message arrives, then resumes it. Zero CPU wasted waiting.

CACHING LAYER

Redis — the hot path

What's stored

price:AAPL

price "250.03"

bid "250.01"

ask "250.05"

last_updated "2026-03-30T..."

source "trade"

One hash per symbol. HSET to write, HGETALL to read. Both O(1).

Why not just query the DB?

  • DB query = index scan + connection + network = 2–5ms
  • Redis = RAM lookup = 0.2ms
  • At 100 users × 1 req/s = 100 DB queries/s just for latest price
  • Redis handles that with zero sweat

The tradeoff

Redis is up to 500ms ahead of TimescaleDB (the batch window). If the ingestor crashes, Redis has prices the DB doesn't. Acceptable for a display — not for executing a trade.

PERSISTENCE LAYER

TimescaleDB — the cold path

Why not plain PostgreSQL?

  • Hypertables — auto-partitions by time. Query "last hour" → scans only that chunk, not the whole table
  • time_bucket() — built-in OHLCV aggregation with first() and last() functions
  • Compression — chunks older than 7 days compress 90%+
  • Retention policies — auto-drop chunks after 90 days

Schema

ticks (hypertable, partitioned by time)

  time        TIMESTAMPTZ  ← partition key

  symbol      VARCHAR

  price       NUMERIC(18,6)

  bid, ask    NUMERIC(18,6)

  volume      BIGINT

  source      VARCHAR

Batch writes — why not one-by-one?

At market open, AAPL generates hundreds of ticks per second.

ONE-BY-ONE

500 ticks/s = 500 DB round-trips/s = connection pool saturated in seconds.

BATCH (500MS)

500 ticks → 1 INSERT … VALUES (…),(…),(…) statement. One WAL entry. One round-trip.

Latency cost: ticks land in Redis instantly. DB is 500ms behind. For a price display, invisible.

CONCURRENCY MODEL

asyncio — one thread, many tasks

Three tasks, one event loop

# startup in main.py

asyncio.create_task(run_ingestor())  # ①

await start_feed()                   # ② ws task

# FastAPI handles HTTP requests        # ③

All three run concurrently in one thread. The event loop switches between them whenever one is waiting on I/O (network, DB, sleep).

Why this works for I/O

  • WS receive is waiting on network → event loop runs ingestor
  • DB write is waiting on disk → event loop runs HTTP handler
  • They never actually run at the same time — they take turns
  • No threads = no locks, no race conditions, no GIL fights

Would fail for CPU-heavy work. asyncio is I/O concurrency only — PDF generation, image processing, ML inference would block the loop.

FRONTEND

React UI

Price Board — left panel

  • Polls /tickers every 1 second
  • Compares new price to previous → flashes green or red
  • Tracks first price seen as session open → calculates change %
  • Click a symbol → opens history panel

History Panel — right panel

  • Polls /ticks/{sym} every 5 seconds
  • Line chart — every tick plotted as a point (lightweight-charts)
  • Table — newest first, time + price + bid/ask + source
  • Source column: trade or quote

Why Vite + React?

  • State-driven — price flashes, selection state, loading states all managed cleanly with useState
  • useEffect — polling intervals that clean up properly on unmount, no memory leaks
  • HMR — Vite hot-reloads the UI instantly on save while the API keeps running
  • TypeScript — API response types match backend Pydantic models, caught at compile time

Dev server on :5173, API on :8000. CORS middleware on FastAPI allows localhost:5173. In production they'd be same origin.

WHAT'S MISSING

Production gaps

Scaling the feed

Single WebSocket connection per process. To scale horizontally: publish ticks to Redis Streams or Kafka, run N ingestor workers consuming from the queue. Feed failure doesn't stop ingestion.

No authentication

All API endpoints are public. Production needs JWT tokens or API key middleware. Secrets (Alpaca keys, DB password) move from .env to AWS Secrets Manager or equivalent.

Observability

Prometheus metrics — ticks/sec, queue depth, ingest latency, DB pool usage. Structured JSON logs → CloudWatch or Loki. Alert if feed disconnects for >5 minutes.

DB optimizations

Continuous aggregates — pre-compute 1m/5m/1h OHLCV as a materialized view so history queries don't scan raw ticks. Compression after 7 days. Retention policy drops chunks older than 90 days.

WebSocket push API

Instead of the UI polling every second, a FastAPI WebSocket endpoint streams price updates to browser clients the moment they arrive. Eliminates polling overhead entirely.

Rate limiting

The /history endpoint runs a time_bucket() aggregation on potentially millions of rows. Without rate limiting, one client can saturate the DB. slowapi — 30 req/min per IP.
